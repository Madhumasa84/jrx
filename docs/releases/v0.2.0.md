# JEV Reflex v0.2.0

JEV Reflex evaluates proposed coding-agent commands and MCP tool calls before execution. This release adds a policy-impact PR check that shows which historical decisions a proposed policy would change.

- **Review the effect of policy edits.** The head commit status shows replay coverage, new ALLOWs, HOLD-to-REVIEW transitions and new HOLDs. The workflow summary includes six transition counts and skipped records. Set independent limits on new ALLOWs and all relaxations. [Policy impact setup](../policy-impact.md)
- **Replay signed evidence in CI.** Use the producer’s public key to verify decision signatures while keeping its private key on the collector. Policies that require signatures fail closed when verification cannot run.
- **Keep private evidence out of fork PRs.** A detection job checks Git merge parents and bounded regular policy blobs. Eligible same-repository changes enter the evidence environment and run the trusted, installed CLI. Replay rejects unsupported changes and zero coverage.
- **Choose an integration.** Route agent calls through a host hook or the stdio MCP gateway. The interactive workspace and managed harness are optional host tools. [Agent integrations](../harnesses.md) · [MCP argument policy](../mcp-argument-policy.md)

## Installation

Requires Python 3.11 or newer. Once the distribution is published, install with `uv tool install jev-reflex==0.2.0` or `pipx install jev-reflex==0.2.0`. Before publication, use the source instructions. [Installation and quickstart](../../README.md#quickstart)

## Staging and publication

Run the policy-impact staging checks on a repository whose trusted `main` contains this workflow, its helper and a configured `policies/agent.yaml`. Complete the evidence setup first. Use a representative snapshot and a candidate previously assessed locally. A changed policy alone does not guarantee a changed decision.

In a clone of that staging repository, set `JRX_STAGING_CANDIDATE` to the path of the assessed candidate YAML. These commands open separate PRs for the two workflow paths.

```bash
git fetch origin main
git switch -c staging/jrx-unchanged origin/main
printf '%s\n' 'Staging fixture for the unchanged-policy check.' > staging-policy-status.md
git add staging-policy-status.md
git commit -m "Stage the unchanged-policy PR status"
git push -u origin HEAD
gh pr create --base main --head staging/jrx-unchanged --title 'Stage unchanged policy' --body 'Expect Policy file unchanged. Verify only detect runs.'

git switch -c staging/jrx-changed origin/main
cp "${JRX_STAGING_CANDIDATE:?set the assessed candidate path}" policies/agent.yaml
git add policies/agent.yaml
git commit -m "Stage policy replay"
git push -u origin HEAD
gh pr create --base main --head staging/jrx-changed --title 'Stage policy replay' --body 'Compare the head status and workflow summary with local replay.'
```

For the fork check, set `STAGING_FORK` to your staging fork as `owner/repo` and `STAGING_REPO` to its upstream `owner/repo`. Use a distinct head commit so its status cannot overwrite the same-repository test’s status.

```bash
git switch -c staging/jrx-fork staging/jrx-changed
git commit --allow-empty -m "Stage fork policy detection"
git push "https://github.com/${STAGING_FORK:?set staging fork}.git" HEAD:refs/heads/staging/jrx-fork
gh pr create --repo "${STAGING_REPO:?set staging upstream}" --base main \
  --head "${STAGING_FORK%%/*}:staging/jrx-fork" --title 'Stage fork policy detection' \
  --body 'Expect a maintainer-PR status. Verify replay skips the evidence environment.'
```

Check the environment deployment history and head commit statuses in addition to the Actions job result.

From the release worktree, submit the production change for review.

```bash
git push -u origin release/0.2.0-launch-hardening
gh pr create --base main --head release/0.2.0-launch-hardening --title 'Harden policy impact for v0.2.0' --body 'Review signed audit replay, relaxation limits, PR evidence isolation and the v0.2.0 packaging checks.'
```

After staging and review, tag the **reviewed merge commit**. Set `RELEASE_PR` to the merged production PR number before running the following in Bash.

```bash
test "$(gh pr view "${RELEASE_PR:?set merged PR number}" --json state --jq .state)" = MERGED &&
  release_commit=$(gh pr view "$RELEASE_PR" --json mergeCommit --jq .mergeCommit.oid) &&
  git fetch origin main &&
  git merge-base --is-ancestor "$release_commit" origin/main &&
  git tag -a v0.2.0 "$release_commit" -m 'JEV Reflex v0.2.0' &&
  git push origin refs/tags/v0.2.0
```

The tag triggers `release.yml`. Its CI verifies the installed version, then the release job builds and pushes the amd64/arm64 broker image to GHCR, signs the digest, attaches the SBOM attestation, and uploads Python distributions to the GitHub Release. GitHub Actions needs package write and OIDC permissions. Inspect the run before publishing the same artifacts to PyPI.

```bash
gh run list --workflow release.yml --commit "$(git rev-list -1 v0.2.0)" --event push
gh run watch "${RELEASE_RUN_ID:?set the tag run ID}" --exit-status
gh release view v0.2.0
docker buildx imagetools inspect ghcr.io/madhumasa84/jrx-broker:0.2.0

release_dist=$(mktemp -d)
gh release download v0.2.0 --dir "$release_dist" --pattern '*.whl' --pattern '*.tar.gz'
uvx --from twine twine check "$release_dist"/*
uvx --from twine twine upload --repository pypi "$release_dist"/*
```

Use PyPI credentials scoped to the `jev-reflex` project where available. Publishing a version on PyPI is permanent.
